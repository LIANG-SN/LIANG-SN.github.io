LLM Stack: Research, Infrastructure & Engineering Roles

From raw data to a reliable product: what each stage does, who builds it, and how research and infrastructure fit together.

Shengnan Liang · Technical overview · Sources checked Oct 26, 2026
Explore the map ↓Compare roles ↓中文速读 ↓
01 / The map

One lifecycle, two connected kinds of work

A general-purpose LLM begins as a learning system and becomes part of a production system. Data, pretraining, post-training, evaluation, inference, deployment, and monitoring all shape the result. An excellent checkpoint can still produce a poor product if retrieval, tool execution, latency, or reliability fails.

Research asks what data, architectures, objectives, and experiments improve capability and behavior. Infrastructure makes those experiments and products run efficiently, reproducibly, and reliably. Research engineering connects the two: implementing an idea, diagnosing its behavior at scale, and making the result usable.

The boundaries are permeable. Inference powers RL rollouts before a model is deployed. Evaluation runs throughout training. Compression can involve training. Production failures can lead back to data, objectives, infrastructure, or application design.

The lifecycle below is a synthesis of public technical reports, framework documentation, and job descriptions checked on October 26, 2026. It is not a claim about any company's undisclosed training recipe. Named models are explanatory examples, not a leaderboard.

02 / Data

Turn raw material into a learning signal

Data work starts with provenance and permitted use, then moves through ingestion, parsing, quality filtering, deduplication, tokenization, and mixture design. A corpus with more tokens is not automatically a better corpus. Researchers ask which domains, languages, difficulty levels, and synthetic examples improve generalization; engineers make the resulting dataset traceable and reproducible.

Typical roles: data research scientist, data engineer, pretraining data infrastructure engineer, and human-data operations specialist. Core skills include Python, SQL, distributed processing, sampling, data-quality analysis, and experiment design. Human-data teams additionally design annotation instructions, manage reviewer disagreement, and audit label quality.

Deliverable: a versioned corpus or preference dataset with lineage, quality checks, and a documented mixture. Holdout evaluation data must be protected from training contamination. The Llama 3 report is a concrete model-development reference; Anthropic's Pre-training Data Infrastructure Engineer JD explicitly spans tokenization, deduplication, validation, and distributed pipelines.

03 / Pretraining

Learn a general foundation—and keep the run alive

For many autoregressive language models, pretraining predicts the next token over broad data. Research choices include architecture, tokenizer, data mixture, optimizer, learning-rate schedule, context length, and how to allocate a compute budget. Continued pretraining can extend domain knowledge or adapt the training distribution; it is distinct from instruction tuning.

Pretraining researchers design controlled experiments and analyze loss, downstream capabilities, scaling, and stability. Training systems engineers implement distributed execution, memory sharding, communication, checkpointing, and recovery. GPU kernel and compiler engineers improve the operators underneath both training and inference. Skills range from probability, optimization, and PyTorch/JAX to CUDA/Triton, profiling, collective communication, and distributed failure diagnosis.

Data parallelism distributes examples; tensor parallelism splits tensor computation; pipeline parallelism splits layers; expert parallelism distributes mixture-of-experts components. The right combination depends on the model and hardware topology. NVIDIA Megatron Core is an industry example of the software supporting this work.

Deliverable: a reproducible base checkpoint and evidence that the run used compute effectively. Tokens per second and utilization matter, but so do training stability, recovery time, and capability gained per unit of compute. Anthropic's Pre-training Research Engineer / Scientist JD combines model design with infrastructure optimization—evidence that research and systems are not cleanly separated job families.

04 / Post-training

SFT, preference learning, and RL solve different problems

Post-training shapes a base model into a more useful assistant, reasoner, or tool user. A recipe may combine several methods and repeat them. The sequence is a design choice, not a mandatory assembly line.

Common post-training methods
MethodLearning signalWhat the team actually builds
SFT
Supervised fine-tuning		Demonstrations of desired responses or trajectories; typically a token-level likelihood objective.Instruction datasets, conversation formatting, loss masks, tool-use examples, and regression evaluations.
DPO
Direct preference optimization		Preferred versus dispreferred responses, optimized directly with a preference objective.Preference pairs, reference-policy handling, data audits, and preference/generalization checks. Standard offline DPO does not require an online rollout-and-reward-model loop.
RLHF / RLAIFRewards informed by human or AI feedback, often through a learned preference model.Reward models or graders, sampled responses, policy updates, and checks for reward exploitation. The feedback source does not by itself specify the optimizer.
RL with verifiable rewardsProgrammatic checks such as answer correctness or executable tests.Task generators, verifiers, sandboxed environments, rollout pipelines, and policy optimization. A passing test remains a proxy for the intended task.

The DPO paper explains direct preference optimization. Learning to Summarize from Human Feedback illustrates the learned-reward approach. DeepSeek-R1 provides a useful contrast: R1-Zero explores RL without preliminary SFT, while R1 incorporates cold-start data and a multistage recipe. Neither establishes that every model should follow the same path.

Post-training scientists and applied scientists study behavior, data mixtures, reward design, and capability trade-offs. Research engineers implement and operate the recipe. RL infrastructure engineers coordinate sampling, environments, verifiers, weight synchronization, training, and evaluation. Skills include optimization, experimental design, Python, distributed ML, and careful error analysis.

RL is also an inference workload: the policy repeatedly generates candidate trajectories. A faster rollout engine may enable more experiments, while stale weights, long-tail environment delays, or unreliable graders can undermine learning. Anthropic's RL Engineering JD explicitly crosses orchestration, environments, training, inference, and evaluation. Its Production Model Post-Training JD emphasizes turning recipes into reliable production models.

Deliverable: an improved checkpoint plus reproducible evidence of the improvement. Training reward alone is insufficient: independently evaluate task success, robustness, and regressions. Keep graders and hidden tests outside the policy's control.

05 / Evaluation

Decide whether an improvement is real

Evaluation is a continuous function, not just a final exam. Before training, it helps define success. During training, it detects regressions. Before release, it supports a go/no-go decision. After release, it connects offline measurements to real use.

Evaluation researchers define constructs and trustworthy metrics; evaluation engineers build repeatable runners, datasets, dashboards, and grading systems; safety and security specialists probe harmful behavior, prompt injection, and permission failures. Core skills include statistics, experimental design, dataset curation, distributed execution, and adversarial testing.

Measure distinct dimensions: task correctness, factuality, instruction following, tool success, multilingual quality, safety, latency, and cost. Report uncertainty where appropriate, inspect failure slices, and keep prompts, model versions, sampling settings, and graders versioned. A model judge needs calibration against human or objective checks; it is not automatic ground truth.

Deliverable: a release scorecard with known failure modes and explicit acceptance criteria. Anthropic's Post-Training Model Evaluations JD illustrates this connection: live training measurements, regression investigation, dashboards, and guidance for training and release decisions.

06 / Inference & serving

Make capability affordable at the required latency

Inference executes a model. Serving manages requests around it: batching, scheduling, caching, routing, and capacity. Prefill processes the prompt; autoregressive decode generates subsequent tokens. Their bottlenecks depend on sequence length, concurrency, architecture, and hardware.

Inference performance engineers profile bottlenecks and tune runtimes; kernel engineers optimize device-level computation; serving engineers manage request flow and distributed execution. Skills include GPU memory behavior, C++/CUDA or Triton, Python, benchmarking, parallelism, and queueing intuition.

vLLM and SGLang are concrete serving-framework examples. Work may include continuous batching, prefix caching, KV-cache management, speculative decoding, or prefill/decode disaggregation. These are workload-dependent options, not a checklist that guarantees speed.

Model optimization engineers and researchers work across the model/runtime boundary. Quantization reduces numerical precision; pruning removes parameters or structure; distillation trains a student from a teacher's signals or examples. Quantization-aware training involves retraining, while post-training quantization may use calibration without full retraining. Sparse weights only accelerate execution when the hardware and kernels can exploit their structure.

Deliverable: a quality–latency–cost curve under a stated workload. Track time to first token, time between tokens, end-to-end tail latency, throughput, memory, and cost per successful task. A throughput gain that violates the latency target is not a deployment win. NVIDIA's Inference Performance Engineer JD reflects this mix of serving constraints, model execution, and optimization.

Architecture is a systems decision too. The 2026 DeepSeek-V4 report describes attention compression aimed at long-context efficiency. The broader lesson is that architecture changes can alter KV-cache requirements and serving economics. Reported gains are specific to the authors' setup, not universal speedups.

For the provider landscape and the distinction between engines, platforms, and GPU clouds, see the companion article Mapping the AI Inference Stack.

07 / Deployment & applications

A model endpoint is one component of a product

ML platform engineers package and version models, automate deployment, and manage capacity. SREs and production engineers own reliability targets, incident response, rollbacks, and recovery. Edge ML engineers adapt models to device memory, power, thermal, and offline constraints. Skills include containers, orchestration, networking, CI/CD, observability, and runtime debugging.

A release should identify the checkpoint, tokenizer, chat template, quantization configuration, runtime, and evaluation results. Canary releases and rollback paths reduce the impact of regressions. GPU utilization is only one capacity signal: queueing, startup time, and traffic shape also determine user experience. Ray Serve's production guide illustrates orchestration and operational concerns beyond the model engine.

Applied scientists, ML engineers, and agent/product engineers connect the model to retrieval, tools, state, and user workflows. RAG supplies retrieved context; it does not itself update model weights. Tool calling produces an action request; the surrounding software validates and executes it. An agent adds a control loop around model decisions and environment feedback.

These teams use software engineering, information retrieval, evaluation, and domain knowledge. Their deliverable is a working task flow with measured end-to-end success. Tool permissions, timeouts, idempotency, and approval boundaries belong in the execution system. Better model behavior helps, but cannot replace those controls.

Multimodal and speech work cuts across the entire map: researchers design modality representations and objectives, data teams align modalities, runtime teams handle encoders and streaming, and product teams measure perceptual quality and interaction latency. It is a specialization across stages rather than a final layer.

08 / Monitoring & feedback

Close the loop without confusing traffic with truth

Production monitoring has two complementary tracks. System health covers errors, latency percentiles, queue depth, capacity, and cost. Behavior quality covers task completion, retrieval failures, unsafe actions, user corrections, and changes in the input distribution.

Observability engineers and SREs make traces and metrics usable; applied ML and evaluation teams determine what behavior signals mean. Ray Serve's monitoring documentation provides a concrete operational example. A successful HTTP response says little about whether the model solved the user's problem.

Deliverable: actionable alerts, incident analysis, and a prioritized improvement backlog. Route failures to the right owner: missing knowledge may suggest retrieval or data changes; invalid tool arguments may suggest schema or training changes; slow responses may suggest routing, runtime, or capacity changes. Curated feedback can become new training or evaluation data after privacy, quality, and contamination checks. Production traffic should not automatically become training data.

09 / Reading job descriptions

Look for ownership, not just the title

The table below is a practical interpretation of common roles, not a standardized industry taxonomy. Team size and company strategy determine how many responsibilities one person owns. A foundation-model lab, an inference provider, and an application company can use the same title for very different work.

How to recognize a role's center of gravity
Role familyPrimary ownershipEvidence of strength
Research ScientistHypotheses, methods, and empirical findings.Careful ablations, reliable measurements, and insight into why a method works or fails.
Research EngineerExperiments and the systems that make them possible.Correct implementations, fast iteration, reproducibility, and diagnosis across model and system behavior.
Applied Scientist / ML EngineerModel and data choices for a defined task or product.Measured improvements on realistic tasks, production integration, and error analysis.
ML Systems / Infrastructure EngineerShared data, training, or serving infrastructure.Efficiency, reliability, scalable abstractions, and useful researcher/developer tooling.
Performance / Kernel EngineerOperator, model, or end-to-end execution efficiency.Profiles, numerical correctness, reproducible benchmarks, and hardware-aware optimization.
Evaluation / Safety EngineerTrustworthy measurement and failure discovery.Coverage, validated graders, regression diagnosis, and actionable release criteria.
Platform Engineer / SREProduction lifecycle and service reliability.Repeatable releases, capacity planning, incident handling, and recovery.

When reading a JD, ask: What artifact does this person own? What metric defines success? What breaks at scale? Which neighboring team depends on the work? Those questions reveal more than whether the title contains “research” or “infrastructure.” Public job postings show concrete responsibilities; they do not establish market-wide demand, talent scarcity, or a universal career ranking.

10 / Putting it together

Example: shipping a coding assistant

Consider an illustrative coding assistant built on an existing base model. The data team curates permitted code and task trajectories. Post-training researchers compare demonstrations and reward-based learning; RL engineers operate isolated execution environments and rollout workers. Evaluation engineers test unseen repositories and investigate whether passing tests corresponds to real task completion.

Inference engineers profile long repository contexts and generation latency, then test batching or quantization without losing task quality. Product engineers implement repository retrieval, edit tools, and execution permissions. Platform engineers release the version gradually, while monitoring teams track task failures, latency, and cost. A failure to find the right file is routed differently from a model reasoning failure or a GPU capacity problem.

The organization may never pretrain a foundation model. It still touches much of the stack. Conversely, a frontier-model lab needs application-like environments and serving machinery inside its training process. The most useful map is a set of connected responsibilities, with evidence passed between teams.

如何理解这张 LLM 技术栈地图

LLM 的完整生命周期包括：数据 → 预训练 → 后训练 → 评测 → 推理与服务 → 部署 → 监控与反馈。它并非单向流水线：评测贯穿全程，RL 训练需要推理生成 rollout，生产问题也会反向推动数据、算法与系统改进。

Research 研究模型为什么更好、什么数据和目标有效；Infra 让实验和服务高效、可靠、可复现；Research Engineer 常常跨越两者。SFT 学习示范，DPO 直接学习偏好，RL 根据奖励优化策略；它们不是简单的替代关系。

Inference 负责执行模型，Serving 负责请求调度与资源管理，Deployment 负责版本发布和运行环境，Monitoring 同时关注系统健康与任务质量。量化、剪枝、蒸馏、多模态和安全都可能跨越多个阶段。看岗位时，重点看它交付什么、用什么指标衡量，以及和哪些团队协作。
